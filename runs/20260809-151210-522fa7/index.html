# Issue #58 — Harness has no scenario action for player-path hole dig or removal slug: harness-hole-dig-action project: godot-td workspace: godot-td/issue-harness-hole-dig-action branch: issue/harness-hole-dig-action base: task/progression ## Problem A scenario can only create a hole with `{"type": "call", "target": "underground", "method": "add_hole", ...}`, which reaches `UndergroundSystem.add_hole` directly. That is **not** the player path. The real dig flow is `HolePlacementModule.attempt_hole_placement` (`scripts/game/placement/HolePlacementModule.gd:14-28`) -> `HoleRemovalSystem.add_hole_complete` (`scripts/game/systems/HoleRemovalSystem.gd:125-128`) -> `TowerHoleConnectionManager.notify_hole_added`. `add_hole` itself never calls `notify_hole_added`, and neither `HolePlacementModule` nor `HoleRemovalSystem` is a resolvable `call` target — `HarnessActions._resolve_target` (`scripts/testing/HarnessActions.gd:293-313`) only knows `game`, `ui`, `underground`, `cave_system`, `progression`, `towers`, `gamestate`, `strategy_record`. Consequence: everything downstream of `notify_hole_added` / `notify_hole_removed` has **zero** runtime coverage and cannot be given any — `TowerHoleConnectionManager._handle_floodgate_hole_added` (reconnect an unassigned or worse-assigned Floodgate when a hole lands next to it), `_handle_floodgate_hole_removed` and `_handle_porter_hole_removed`. Hole *removal* is unreachable for the same reason: `HoleRemovalSystem.remove_hole` has no scenario entry point either. Found while verifying #51. That fix changed `_handle_floodgate_hole_added`'s connection radius from the tower's own `range` (2.0 for Floodgate) to `HoleRangeIndicator.HOLE_RANGE` (3.0); the corresponding acceptance criterion had to be marked verified-by-code-review-only because no scenario can execute that line. ## Why it matters The hole-added reconnect path is exactly where a Floodgate silently stops flooding — the same failure mode #51 existed to fix on the placement path. A regression there costs the player 400 gold for an inert tower and no scenario in `tests/scenarios/` would go red. The dig UX around it (hole cost deducted, `_clear_dig_mode`, off-path refusal) is untested for the same reason. ## Done when - A `place_hole` scenario action exists (e.g. `{"type": "place_hole", "pos": [x, 0.0, z]}`) routed to `HolePlacementModule.attempt_hole_placement` through a `_hole_placement_module()` helper alongside the existing `_tower_placement_module()` / `_trap_placement_module()` in `scripts/testing/HarnessActions.gd`, returning `{ok, detail}` the way `place_tower` does so an off-path or unaffordable dig reads as a refusal with a reason rather than a silent no-op. - A `remove_hole` action reaches `HoleRemovalSystem.remove_hole`, so `notify_hole_removed` becomes reachable too. - A scenario places a Floodgate **first** and digs the hole **second**, within `HoleRangeIndicator.HOLE_RANGE` of it, and asserts `stats.damage_by_type.floodgate > 0` — i.e. it fails if `_handle_floodgate_hole_added` stops reconnecting. Verified red by temporarily restoring the old `tower.get("range")` limit. - `.claude/skills/game-test/REFERENCE.md` documents both actions. ## Related #51 — the fix whose `_handle_floodgate_hole_added` criterion this gap blocks from being asserted. ## Constraints - Use run_project_cmd with project=godot-td and workspace=godot-td/issue-harness-hole-dig-action for all Godot/harness commands. - Git operations stay Hermes-side outside feature-check agents if needed; agents should implement in the worktree. - Do not close the GitHub issue. - Prefer focused harness scenario under tests/scenarios/.
